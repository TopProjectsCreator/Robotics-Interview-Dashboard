---
name: Supabase CLI browser login protocol and keyring-free multi-account
description: The CLI browser login can be driven directly via the P-256 ECDH + AES-GCM protocol; without an OS keyring, two accounts need separate SUPABASE_HOME stores and wrappers.
---

When the Supabase CLI's interactive `login` cannot be driven from an agent sandbox, implement the browser-login protocol directly instead of fighting PTY input. Generate a P-256 ECDH keypair (`createECDH("prime256v1")`, uncompressed hex public key), a session UUID, and a token name; build `https://supabase.com/dashboard/cli/login?session_id=...&token_name=...&public_key=...`; after the user authenticates and returns the verification code, GET `https://api.supabase.com/platform/cli/login/<sessionId>?device_code=<code>` and expect `{access_token, public_key, nonce}`. Decrypt by computing the ECDH shared secret from the response's server public key, then AES-256-GCM with the response nonce; the 16-byte GCM tag is the last 32 hex chars of `access_token`, the rest is ciphertext. Write the plaintext token to `<SUPABASE_HOME>/access-token` with mode 0600. This is copied verbatim from `apps/cli/src/command-internal/login-crypto.layer.ts`.

**Why:** Piping a code into `script -qec 'supabase login ...'` did not reach the `@clack/prompts` verification-code field — the prompt renders character-by-character over the PTY with raw-mode input, and the code was silently dropped despite `script` forwarding stdin correctly in a plain `cat` test. Direct protocol implementation removed the interactive layer entirely. Also, this container has no D-Bus/Secret Service, so two profiles in one `SUPABASE_HOME` share a single `access-token` file and the second login overwrites the first.

**How to apply:** For two simultaneous logins without a keyring, create one home per account (`~/.supabase-team`, `~/.supabase-personal`) and wrapper scripts `supabase-team` / `supabase-personal` that export `SUPABASE_HOME` then `exec supabase --profile <home>/<name>.yaml "$@"`, installed on PATH. Verify with `<wrapper> whoami`. Keep the ECDH private keys in a temp state file only until the code arrives, then delete them. A 404 from the verification endpoint before the user opens the link is expected because the session is not registered yet.
