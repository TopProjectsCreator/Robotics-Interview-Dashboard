---
name: Supabase CLI multi-account profiles
description: Supabase CLI v3 supports multiple accounts via profiles with per-profile keyring tokens; file fallback shares one token and built-in names are environments, not accounts.
---

Supabase CLI v3 (`supabase`, npm global install) supports being signed into multiple accounts at once through **profiles**, but the mechanism is easy to misread. Select a profile with the global `--profile` flag, the `SUPABASE_PROFILE` env var, or the persisted `~/.supabase/profile` file. Each profile has its own access-token entry in the OS keyring (service `Supabase CLI`, account = the profile's resolved `name`). A successful `login` also writes the active profile's raw token/path to `~/.supabase/profile`, so only ONE profile is active per invocation.

**Why:** The bundled binary's `CommandSettings.resolveProfile` / `CommandCredentials` logic shows token lookup priority `SUPABASE_ACCESS_TOKEN` env → keyring entry for the current profile → shared token file. The keyring write uses the profile name as the account key, which is what allows two accounts to coexist. Built-in profile names are only `supabase`, `supabase-staging`, `supabase-local`, `snap` (different API environments, not accounts); a bare custom name like `work` is treated as a config FILE path and fails with `unsupported config file type ""`. Custom profiles need a YAML/JSON/TOML file with `name`, `api_url`, `dashboard_url`, `project_host`. The `login --name` flag is only the token's label in the dashboard, not local account selection. Critically, when the keyring is unavailable (no D-Bus/Secret Service in this sandbox), all profiles fall back to the SAME `~/.supabase/access-token` file — logging into a second profile overwrites the first, so true simultaneous multi-account requires a working keyring.

**How to apply:** To verify multi-account support, create two profile config files pointing at `https://api.supabase.com` with different `name` values, log in to each with `supabase login --profile <file>.yaml --token sbp_...`, and check `whoami --profile <file>.yaml --debug` for `Using access token for profile: <name>`. If debug says `Using access token from file: .../access-token`, keyring is unavailable and only one account is retained. Also note `login --token` does not validate the token against the API (it only checks the `^sbp_(oauth_|v0_)?[a-f0-9]{40}$` format), so fake tokens can appear to log in successfully.
